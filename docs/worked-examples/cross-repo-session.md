# Worked example: a mail failure triggers a cross-repo session

A synthetic worked example used to validate ispec's cross-repo handling. The projects, identifiers, commit SHAs, and narrative details are invented; the *shape* of the session is drawn from real cross-repo work.

Two repos:

- **`roster`** — a membership-management web app. Sends invoices and campaign mail.
- **`provisioner`** — the deploy tool `roster` uses to ship to its server.

The trigger arrives in `roster`; the work lands in both repos.

## The story

> Mail sending in roster doesn't work — a campaign silently marked every recipient as `sent` while no mail was delivered. The mail provider's client is wired up, but `MAIL_API_KEY` was never configured in the runtime environment.

Investigation surfaces:

- The proximate cause: no `MAIL_API_KEY` in the runtime environment.
- The deeper gap: `provisioner` has no support for encrypted secrets. Hardcoding the key would commit it to git in plaintext — not acceptable.
- Fixing this properly requires giving `provisioner` a sops/age pipeline, then wiring roster's mail key into the encrypted spec.

The session crosses two repos. Six commits land between when the bug is filed and when mail is verified working.

## How the `ispec-start-session` skill would run

### 1. Classify the trigger

Two classifications combined:

- **Bad implementation** in roster: campaign send paths silently succeed when no mailer is configured. A missing `MailerCanDeliver()` guard.
- **New feature** in provisioner: encrypted secret management does not exist; this is a new capability driven by a downstream stakeholder need.

### 2. Search existing cards

In provisioner, no requirement covers "encrypted-at-rest secrets in repo." In roster, no requirement covers "transactional email is reliably sent." Both will be drafted.

### 3. Open a session card

`roster/.ispec/sessions/2026-04-15-fix-mail-sending.md` (originating repo = roster).

### 4. Detect cross-repo work

The agent surfaces: "the proximate cause is in roster, but the structural fix requires changes in provisioner. Both use ispec. We can extend the session to cover both, or hardcode the key in roster for now and defer the provisioner part." User chooses to do it properly: extend.

### 5. Draft the contract

```
In roster:
  - REQ-12: transactional email is sent reliably for invoices and campaigns
  - F-7:    mail provider integration; supports invoices and campaigns
  - F-8:    fail-loud guards (MailerCanDeliver, bounce pre-filter)
  - ADR-0014: chose this mail provider over two alternatives
  - SPEC-email: sender identities, DKIM/SPF/DMARC, guards
  - Depends on provisioner:F-12 (sops pipeline) for key delivery

In provisioner:
  - STK-client-apps (stakeholder): client applications using provisioner to deploy
  - REQ-15: client apps can deploy without committing plaintext secrets to git
            (originated_during: roster:2026-04-15-fix-mail-sending)
  - F-12: unified sops/age pipeline (env + file targets)
  - F-13: per-app host age keypair, auto-generated by provision
  - F-14: encrypted values embedded in deploy.yaml under values:, decrypted host-side
  - F-15: keygen + bootstrap commands for one-shot setup
  - ADR-0007: chose sops+age over alternatives (vault, CI env injection)
  - SPEC-secrets-pipeline: pipeline architecture, recipient list, on-disk layout

Out of scope (deferred):
  - provisioner:F-16: --recover shortcut for bootstrap (separable, not blocking)
  - provisioner:F-17: ops procedure for annual API key rotation
```

User confirms. The contract is the load-bearing artifact: every commit that follows references one of these IDs.

### 6. Apply canon updates to working tree

In provisioner: stakeholder, requirement, feature, ADR, spec cards drafted. In roster: requirement, feature, ADR, spec cards drafted. Cross-repo `depends_on` edges set. Nothing committed yet.

### 7. Implement

Six commits land, in order:

| SHA | Repo | Message | Implements |
|-----|------|---------|------------|
| `a1b2c3d` | provisioner | secrets: unified sops/age pipeline (env + file targets) | F-12 |
| `e4f5a6b` | provisioner | secrets: embed values in deploy.yaml, decrypt host-side at provision | F-14 |
| `c7d8e9f` | provisioner | secrets: per-app host age key (auto-generated by provision) | F-13 |
| `b1c2d3e` | provisioner | secrets: keygen + bootstrap commands for one-shot setup | F-15 |
| `f4a5b6c` | provisioner | secrets: fix encrypted_regex pattern + sops envelope absorber | (bug-fix in F-12; spec amendment to SPEC-secrets-pipeline) |
| `d7e8f9a` | provisioner | roster: add object-storage backup credentials to encrypted spec | (extension; would arguably be a follow-on session) |

Plus roster-side commits configuring the mail key, adding the `MailerCanDeliver` guard, and updating roster's spec.

Note `f4a5b6c`: a bug discovered during implementation. Mid-coding, the agent surfaces: "the `encrypted_regex` pattern as drafted doesn't match the sops envelope structure correctly. Amending SPEC-secrets-pipeline §2.1 to specify the exact regex shape. OK to continue?" User confirms; the amendment lands in the working tree, committed alongside the fix.

### 8. Pre-completion reconciliation

Mail is sent successfully from roster using a key decrypted at provision time. Reconciliation diff finds:

- `F-12` originally said "env-only targets"; implementation added file targets too because a service-account JSON file needed to land on disk. The agent surfaces: "the implementation diverged from F-12's original definition — file targets are also supported now. I've updated F-12 to match. Confirm?" User confirms.

This is exactly the discipline that would otherwise produce silent canon drift.

### 9. Commit

Canon updates land alongside their corresponding code commits where natural; the cross-cutting requirement and stakeholder cards land in their own commits referencing the originating session.

### 10. Suggest closing the session

Tests pass; mail verified end-to-end. Agent suggests `ispec-close-session`.

## What this validates about the design

- **Cross-repo wikilinks and `depends_on` edges work** to express that roster's email feature depends on a provisioner capability. Lint can check both sides — a roster card referencing `provisioner:F-12` requires that ID to exist; conversely, provisioner can search for downstream consumers of any of its features.
- **Origination metadata** (`originated_during: roster:2026-04-15-fix-mail-sending`) traces the *why* of provisioner's new requirement back to a concrete trigger, without making the requirement itself roster-specific. Future provisioner contributors can read REQ-15 as a clean general capability and follow the link if they need context.
- **Stakeholder model** generalizes naturally: "client applications" is one of provisioner's stakeholder cards, with concrete instances referenced as needed.
- **The single-session-spans-two-repos shape** is honest: one session card, one chronological record, but commits land per-repo as git requires. The session card collects the cross-repo commit refs.
- **Mid-implementation amendment** (commit `f4a5b6c` for the `encrypted_regex` fix) is captured as an in-flight spec amendment to SPEC-secrets-pipeline, not as a silent bug fix that lets canon drift.
- **Pre-completion reconciliation surfaced the F-12 env-vs-file divergence** — exactly the kind of "implementation widened the contract" case that silently rots specs in workflows without an explicit reconciliation step.

## What's interesting / what wasn't ideal

- **The backup-credentials commit (`d7e8f9a`) is ambiguous.** It extends the same encrypted-spec mechanism to a new app concern (backups). It could be modeled as part of this session (extending F-12's reach) or as a follow-on session targeting a separate roster requirement (durable backups). Either is defensible. The judgment is whether "encrypted backup creds" is a natural inclusion in this session's scope or a separable concern. Given the timeline (a follow-up commit), modeling it as a follow-on session is probably more honest — it had its own trigger ("set up off-site backups") that happened to land on top of the now-existing pipeline.
- **No ADR superseded.** All provisioner decisions in this session were greenfield. A more interesting case for ADR lifecycle would be a future session that revisits, say, the choice of sops over a vault.
- **The `F-8` fail-loud guard in roster** (the `MailerCanDeliver` check) is a good example of "missed corner case" classification — the spec should always have said "send paths refuse to run when no mailer is configured," but it didn't. The session amends SPEC-email to add this corner case explicitly, so future implementations can't regress to silent success.
